# Wordstat: вкладка «Анализ спроса»

«Анализ спроса» открывается первой вкладкой. «Статистика запросов» сохраняет существующую таблицу и экспорт XLSX. Новая вкладка использует общие фильтры проекта, CSS и Recharts из SEO-аналитики. Отдельного экспорта анализа спроса нет.

## Источник и расчёты

Новая независимая витрина `default.yd_wordstat_demand`:

| Поле | Значение |
|---|---|
| `source` | `all`, `device`, `region` |
| `dimension` | пусто, код устройства или название группы IPLAST |
| `feature`, `category`, `phrase` | категория, подкатегория, запрос |
| `date` | первый день месяца; месяцы хранятся строками |
| `count` | частотность, `Nullable(Int64)` |
| `snapshot` | идентификатор опубликованной версии |

Уникальность факта: `source + dimension + phrase + date`. Она проверяется перед публикацией. Новая вкладка читает только ClickHouse. Старая витрина `yd_wordstat_for` не изменяется командой построения новой витрины.

Периоды 1/3/6/12 месяцев сравниваются с теми же календарными месяцами прошлого года. Рост агрегата считается после суммирования частотностей. Пропуск не равен нулю; дубли не суммируются. При нулевой базе процент отсутствует, статус — «Новый». Нейтральная зона задаётся Django setting `WORDSTAT_DEMAND_NEUTRAL_PERCENT` (по умолчанию 2); минимальная база процентного рейтинга — `WORDSTAT_DEMAND_MIN_BASE` (100). Это settings, не автоматически читаемые переменные окружения.

Сезонность: сначала суммы запросов по месяцам внутри объекта, затем отношение месяца к средней частотности полного года, затем среднее коэффициентов по полным завершённым годам. Текущий год исключён; неполные и полностью нулевые годы не используются. Менее двух пригодных лет сопровождается пояснением. Одновременно до пяти серий; scatter — до 500 объектов с наибольшим объёмом, рейтинги считают по всей выборке.

Карточки разрезов используют месячные данные за выбранный период. Доли считаются от общего спроса, изменения долей — в процентных пунктах. При неполных данных или сумме долей выше 100% структура не показывается как достоверная. При выборе запроса карточки сравнивают его с родительской выборкой; KPI и рейтинги сохраняют контекст списка. Идентификатор версии защищает от смешивания общего спроса и разрезов при параллельной публикации.

## Проверка полноты и обновлений

`python manage.py inspect_wordstat_data` — диагностика без вызовов API, записи данных и уведомлений. Проверяет последние 24 завершённых месяца: общий спрос, 3 устройства и 7 групп IPLAST, количество уникальных запросов, пропуски, дубли и суммы между PostgreSQL и ClickHouse. Отдельно показывает устаревшие/отсутствующие checkpoints и региональные строки с неактуальным `group_fingerprint`. Команда не приравнивает импортированную историю без checkpoints к подтверждённой загрузке API.

`python manage.py inspect_wordstat_data --deep` дополнительно проверяет сохранённый интервал каждого checkpoint; это много запросов к PostgreSQL. Обе команды только читают данные. Обычный `check_table_health` теперь вызывает базовую диагностику Wordstat; сам Table Health по-прежнему отправляет штатное уведомление. Пока месячная загрузка не закончена, проверка может сообщать о неполноте — наличие строк больше не означает успешную загрузку.

В селекторе доступны все завершённые месяцы до предыдущего календарного месяца. Неполные и отсутствующие месяцы помечены; текущий месяц исключён. Последний полный месяц определяется внутри выбранной категории, а не по всему справочнику. Пропуски не превращаются в нули. Карточки показывают причину отсутствия структуры и месяцы, по которым нет полного набора запросов.

Отчёты кэшируются на 5 минут с ключом опубликованного `snapshot`; после замены витрины старый кэш не используется. Статистика имеет отдельное поколение ключей, чтобы незавершённый старый запрос не восстановил актуальный кэш после сброса. Самостоятельный `sync_wordstat_demand` отправляет событие обновления. В полном конвейере публикация статистики сбрасывает кэш ещё до построения новой витрины: ошибка второго этапа не оставляет старую статистику в кэше.

Вкладки загружаются независимо и только при активации; возврат на вкладку перечитывает данные. После переподключения сокета, возвращения к окну браузера или восстановления сети Wordstat обновляется. Фильтры статистики сохраняются; страницы при обновлении читаются заново с первой, чтобы не смешивать разные публикации. `metadata_only=1` у builder возвращает оболочку Wordstat без запроса старой таблицы; обычный builder и XLSX-экспорт продолжают работать.

## Построение витрины

Команда меняет только новую витрину ClickHouse. Она не вызывает Wordstat, не расходует API-квоту и не изменяет исходные таблицы PostgreSQL:

```bash
docker exec analytics-django python manage.py sync_wordstat_demand
```

Источники:

1. Общая история — существующие `month_1`…`month_12` и `year` из `default.yd_wordstat_for`, преобразованные в месячные строки.
2. Устройства — сохранённые месячные строки `yd_wordstat_device` в PostgreSQL.
3. IPLAST — `yd_wordstat_iplast_api` в PostgreSQL; берутся только строки с актуальным отпечатком состава группы.
4. Иерархия и действующий список фраз — PostgreSQL `yd_wordstat_ref`; состав групп — `yd_wordstat_ref_iplast`.

Сначала должны быть применены миграции существующего перехода на Wordstat v2. Для этой вкладки новых миграций Django нет. При отсутствии новой витрины интерфейс показывает пустое состояние; для разрезов без истории показывается недостаток данных.

Построение использует общую блокировку загрузчика: нельзя одновременно запускать его с загрузкой API. Не меняйте справочники во время построения. После полной загрузки API витрина обновляется автоматически; отдельные `--source` загрузки её не публикуют.

Публикация: временная таблица → сверка количества строк, количества непустых значений, общей суммы и уникальности ключей → `EXCHANGE TABLES`. Для базы `default` требуется движок `Atomic` или `Shared`; переключение имён атомарно ([документация ClickHouse](https://clickhouse.com/docs/reference/statements/exchange)). При ошибке до переключения прежняя новая витрина остаётся доступной. Это не изменяет прежний механизм публикации старой вкладки.

## Проверка после заполнения

```sql
SELECT source, count(), uniqExact(phrase), min(date), max(date), sum(count)
FROM default.yd_wordstat_demand
GROUP BY source ORDER BY source;
```

В результате команды `rows` и `by_source` должны соответствовать числу строк в ClickHouse. Для выборочных фраз сверить `all` с исходными месячными колонками старой витрины, `device`/`region` — с соответствующими месячными строками PostgreSQL. Проверить 1 и 12 месяцев, границу года, нулевую базу, детализацию, карточки, CSV и вторую вкладку. Само совпадение общих сумм не доказывает правильность каждой строки.

## Как использовать старую историю без повторных API-запросов

Простого копирования всех старых таблиц недостаточно:

- `yd_wordstat_all` и `yd_wordstat_device` сохранились; это не новые модели. Перенести/объединить данные без дублей по фразе, месяцу и устройству.
- Для `yd_wordstat_iplast_api` нужна месячная история семи групп. Старые данные по отдельным регионам предварительно агрегируются по согласованному непересекающемуся составу IPLAST. Нельзя считать отсутствующий регион нулём. История старых групп подходит только при совпадающем составе.
- В IPLAST заполнить `group_fingerprint`, соответствующий текущему составу группы. Без него история не считается актуальной.
- Чтобы **API-загрузчик** считал импорт завершённым и пропускал запросы, после проверки полноты нужны корректные записи `yd_wordstat_api_checkpoint`. Отдельной команды импорта/проставления этих отметок в этой доработке нет. Не создавайте их до проверки каждого месяца и каждого разреза.
- Если требуется лишь показать уже сохранённую историю в новой вкладке, отметки API не нужны: достаточно корректных источников и `sync_wordstat_demand`. Это не гарантирует, что последующий запуск API не обновит последние месяцы.

Миграция `0065` удаляет старые региональные таблицы. Переносить/сравнивать их историю нужно по сохранённой копии; обратная миграция данные не восстанавливает.

## Локальные проверки

`python -m unittest tests.test_wordstat_demand tests.test_wordstat_v2` — из `services/backend`, с изолированными тестовыми настройками. Проверки не обращаются к настоящим БД/API. Проверки интерфейса выполняются на синтетических ответах; настоящее серверное наполнение и `EXCHANGE TABLES` нужно проверить после развёртывания.
