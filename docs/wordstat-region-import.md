# Wordstat: перенос регионального архива и дозагрузка

## Что находится в проверенном архиве

Локальный `yd_wordstat_region.zip` проверен потоком, без распаковки. CSV — 3 817 178 638 байт, 13 503 605 строк, 1433 фразы и 94 региона. Дубликатов ключа «фраза — регион — месяц», некорректных дат и отрицательных частотностей не найдено.

| Период | Строк за месяц | Полнота |
| --- | ---: | --- |
| Январь 2018 — май 2025 | 134 702 | Все 1433 × 94 |
| Июнь 2025 — апрель 2026 | 134 701 | Не хватает одной пары в каждом месяце |
| Май 2026 | 33 416 | Частичная загрузка |
| Июнь — август 2026 | 0 | В архиве отсутствуют |

Это архив отдельных регионов, не готовая таблица IPLAST. Нельзя просто выполнить `COPY` этого CSV в `yd_wordstat_iplast_api`: нужны суммы полного состава регионов каждой группы и правильный `group_fingerprint`. Общего спроса и устройств в этом архиве нет; их история переносится отдельно в существующие `yd_wordstat_all` и `yd_wordstat_device` без дублей.

## Перед пушем: ZIP уже в локальном коммите

На момент проверки ZIP входит в единственный неотправленный коммит `344247e` (`Update 22.1`), а в `origin/dev-current` его нет. Удаление ZIP следующим коммитом не уберёт большой объект из отправляемой истории.

Если этот коммит всё ещё последний и не отправлен, выполните локально из корня проекта:

```powershell
git status
git log --oneline origin/dev-current..HEAD
git diff --cached --name-only
```

При пустом индексе исключите **только ZIP** из последнего коммита, сохранив файл на диске:

```powershell
git rm --cached -- yd_wordstat_region.zip
git commit --amend --no-edit
```

Остальные незакоммиченные изменения сохранятся. Не выполняйте `amend` по этой инструкции, если коммит уже отправлен или после него появились другие коммиты: сначала нужно пересмотреть историю. Затем перенесите ZIP на сервер, удалите или переместите локальную копию по своему решению и отдельно закоммитьте нужные изменения кода. Пуш выполняете вы; принудительный пуш для описанного случая не нужен.

## Перенос и пробная проверка

1. Сначала отправьте код и заберите его на сервере в `/opt/analytics-platform` обычным `git pull --ff-only`. Примените штатные миграции проекта: таблица `yd_wordstat_iplast_api` и действующие справочники должны существовать. Новых миграций именно для команды импорта нет.
2. Остановите плановые запуски Wordstat на время импорта. Общая advisory-блокировка дополнительно не даст команде выполняться одновременно с загрузчиком.
3. Перенесите ZIP отдельно от Git. В локальном PowerShell, из каталога с архивом:

```powershell
scp .\yd_wordstat_region.zip jino-codex:/tmp/yd_wordstat_region.zip
```

На сервере проверьте свободное место, в том числе на разделе Docker/PostgreSQL. Импорт создаёт временную PostgreSQL-таблицу всего CSV, индексы и агрегаты; требуется место сверх размера ZIP. Распаковки в файл не будет, но временные таблицы и операции сортировки занимают несколько гигабайт. Сделайте штатную резервную копию PostgreSQL перед импортом.

Из `/opt/analytics-platform` запустите проверку с откатом. Используется существующий образ сервиса `django` и архив, подключённый только для чтения:

```bash
docker compose run --rm --no-deps \
  -v /tmp/yd_wordstat_region.zip:/tmp/yd_wordstat_region.zip:ro \
  django python manage.py import_wordstat_regions \
  /tmp/yd_wordstat_region.zip --through 2026-04
```

Без `--apply` команда проводит COPY во временную таблицу, проверки и подсчёт новых агрегатов внутри транзакции, затем откатывает временные изменения. В постоянные таблицы проверка не вставляет строки. Это не мгновенная проверка: весь CSV читается и PostgreSQL выполняет агрегацию. Она не вызывает Wordstat, ClickHouse, сокеты и уведомления. При ошибке импорта постоянные данные также откатываются.

Команда проверяет заголовки CSV, уникальность ключей, даты, значения, совпадение региональных групп и фраз с действующими справочниками. Изменившийся состав IPLAST нельзя молча считать той же историей. Суммирование регионов предполагает согласованный непересекающийся состав; штатная API-загрузка дополнительно проверяет его по дереву регионов до запросов статистики.

Для каждого сочетания «фраза — группа» импортируется непрерывная история от начала архива до первого неполного месяца. Отсутствующая строка региона не становится нулём. Поэтому почти полный июнь 2025 не считается полным для затронутой группы; её недостающее продолжение восстановит API. Май 2026 намеренно не берём из частичного архива.

Результат проверки содержит:

- `eligible_aggregates` — пригодные месячные агрегаты;
- `inserted` — сколько новых строк было бы добавлено;
- `incomplete_phrase_groups` — сколько сочетаний имеют пропуск до апреля включительно;
- `existing_different_counts_preserved` — сколько существующих значений отличаются от архива и сохранены без перезаписи;
- `mode: dry_run_rollback` — постоянные изменения отменены.

При несовпадении состава групп, неизвестных фразах или другом `group_fingerprint` существующих строк команда останавливается. Такие расхождения нужно разобрать, а не обходить подстановкой отпечатка.

## Импорт и дальнейшее обновление

Повторите ту же команду с `--apply` после успешной проверки:

```bash
docker compose run --rm --no-deps \
  -v /tmp/yd_wordstat_region.zip:/tmp/yd_wordstat_region.zip:ro \
  django python manage.py import_wordstat_regions \
  /tmp/yd_wordstat_region.zip --through 2026-04 --apply
```

Существующие строки не перезаписываются (`ON CONFLICT DO NOTHING`). Повторный запуск не создаёт дубликатов. Справочники и checkpoints не изменяются, витрины не публикуются.

Далее проверьте план и сохранённые данные без API-запросов:

```bash
docker exec analytics-django python manage.py load_yd_wordstat_api --plan
docker exec analytics-django python manage.py inspect_wordstat_data
```

До дозагрузки диагностика ожидаемо сообщит о пропусках и старых checkpoints. Запустите вручную DAG `yd_wordstat_api_full` в Airflow. Одного снятия с паузы недостаточно для гарантированного немедленного старта. В Airflow должно быть `ENABLE_EXTERNAL_API_LOADS=true`, в Django — `YD_WORDSTAT_V2_LOAD_ENABLED=true`; иначе настоящая загрузка не выполняется.

### Откуда начнётся скачивание

При запуске в **сентябре 2026** целевой конец — **31 августа 2026**, а не текущий сентябрь. Загрузчик штатно обновляет последние 12 завершённых месяцев. Для сочетания с сохранённой непрерывной историей до апреля 2026 запрос обычно будет **с сентября 2025 по август 2026**, а не только с мая. Если история обрывается раньше, начало сдвигается к следующему месяцу после последнего сохранённого до окна перезагрузки. При пустой истории — январь 2018. Повреждённый диапазон checkpoint тоже может расширить запрос назад.

Импорт избавляет от повторного запроса всей региональной истории с 2018 года; он не отменяет штатное обновление последних 12 месяцев. Если не перенесены общий спрос или устройства, для них история может запрашиваться с 2018 года. План показывает количество незавершённых сочетаний и целевой месяц; он не выводит индивидуальное начало каждого запроса.

### Как работает многодневная загрузка и публикация

Целевой месяц фиксируется в начале запуска. Каждый ответ сначала проверяется на полный набор месяцев, затем сохраняется в PostgreSQL одной транзакцией вместе с checkpoint. Между запросами могут быть длительные ожидания квоты; её состояние хранится в PostgreSQL и переживает перезапуск. Сохранённые и проверенные сочетания при повторном запуске для того же целевого месяца пропускаются.

Только после завершения и проверки **всех** сочетаний общего спроса, трёх устройств и семи IPLAST-групп пересобирается PostgreSQL-витрина и публикуются ClickHouse-витрины. Во время скачивания дашборд показывает предыдущую публикацию. Каждая ClickHouse-таблица загружается через staging и заменяется атомарно. Общей транзакции на две витрины нет: при ошибке второй первая уже обновлена, а вторая сохраняет прежнюю полную версию; запуск нужно повторить.

DAG ограничен десятью днями и `max_active_runs=1`; автоматических повторов задачи сейчас **нет (`retries=0`)**. После окончательной ошибки/таймаута требуется повторный запуск. Внутри HTTP-клиента есть ограниченные повторы временных ошибок. При запуске уже в следующем календарном месяце целевой месяц изменится.

По окончании:

```bash
docker exec analytics-django python manage.py inspect_wordstat_data --deep
```

Проверьте `ok`, списки пропущенных месяцев, checkpoints, актуальность отпечатков и совпадение PostgreSQL/ClickHouse. Table Health использует базовую диагностику последних 24 месяцев; `--deep` дополнительно проверяет интервалы checkpoints. Это не утверждение о полноте каждого месяца всей истории с 2018 года. Сам `inspect_wordstat_data` уведомления не отправляет.

Проверьте обе вкладки, август 2026, периоды 1/3/6/12, регионы/устройства и сезонность 2026. После публикации текущего года должны отображаться январь–август, а не будущие месяцы.

## Границы выполненной локальной проверки

Архив полностью прочитан локально; расчёты и поведение публикации проверяются автономными тестами, фронтенд собирается. Полный PostgreSQL COPY/SQL этой команды и реальный ClickHouse EXCHANGE на сервере локально не выполнялись. Поэтому первым серверным шагом импорта предусмотрен запуск с откатом. Базы и контейнеры сервера в ходе этой доработки не менялись.
