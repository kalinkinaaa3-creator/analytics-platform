# СУЦ Селект Маркета: локальная проверка и порядок переноса

16.10.2026: подготовлен отдельный Git staging для СУЦ. В индекс включены только
подключения СУЦ в settings/urls/DashboardRenderer; подключения СПС остаются в
рабочей папке вне индекса. Тестовые настройки СУЦ больше не импортируют СПС.
Переносить нужно согласованный коммит из этого индекса, а не всю рабочую папку.
Общие модели и миграции схемы select_market включены как зависимости СУЦ.
Предупреждение о смешанной рабочей папке ниже сохраняет силу при ручном копировании.

Проверено 15.10.2026. Этот документ не подтверждает готовность рабочей БД:
сервер не подключался, рабочие миграции, загрузки и парсеры не запускались.

## 1. Собрать согласованный комплект

Переносить один согласованный комплект backend/frontend, не отдельные файлы по
выводу `git diff`. В рабочей копии новые каталоги и миграции пока untracked.
Обычный commit только отслеживаемых правок их не включит.

Нужны:

- `services/backend/select_market/`, включая все миграции 0001–0012;
- общие изменения `datasets`, новые `iprice_workspace.py`, `parser_queue_models.py`,
  `services/parsers/{global_queue,queue_execution,queue_recovery}.py`;
- новые management-команды Селект Маркета и восстановления очереди;
- миграции `datasets/0071_*`, `0072_*` и их зависимости;
- изменения настроек, URL и подключения моделей;
- `services/frontend/src/iprice/selectMarket/`, изменения подключения дашборда
  и сообщения очереди в Ай-Пласте;
- зависимости Python/Node и необходимые модули существующей платформы.

**Зависимость от СПС:** текущие `config/settings.py`, `config/urls.py` и React
подключают СПС. На сервере должен присутствовать совместимый комплект `sps`
и его frontend. Если его ещё нет, перенос только СУЦ с текущими общими файлами
недостаточен. Состав такого релиза необходимо выделить отдельно до копирования.
Не включать архивы демо, входные Excel, локальные `.env`, тестовые зависимости,
`node_modules` и локальные журналы в приложение.

## 2. Сначала проверить PostgreSQL-стенд

Использовать отдельный сервер/контейнер PostgreSQL и отдельного тестового
пользователя с правом создания БД. Настройки не читают рабочие реквизиты:
`IPRICE_TEST_HOST`, `IPRICE_TEST_PORT`, `IPRICE_TEST_USER`, `IPRICE_TEST_PASSWORD`.
Django создаёт/удаляет `test_iprice_acceptance`; это имя нельзя использовать
для реальных данных. Команда из `services/backend`:

```sh
python manage.py test select_market.test_iprice_postgres --settings=select_market.iprice_postgres_settings
```

Отдельно проверить обновление копии рабочей БД: миграции архивируют и удаляют
устаревшие таблицы/поля Селект Маркета. Сохранность архива, исходных цен,
маршрутов и старых согласований должна проверяться на данных этой копии.
Чистая тестовая БД не заменяет проверку обновления существующей установки.

## 3. Подготовить окно переноса

1. Сохранить предыдущий комплект приложения/образы и серверный `.env`.
2. Запретить новые ручные загрузки, расчёты и запуски парсеров; приостановить
   соответствующие DAG Ай-Пласта и Селект Маркета.
3. Дождаться завершения уже запущенных задач, включая удалённую ТАРА.
   `tara_session_dispatcher` / `process_tara_jobs` оставить работающими,
   пока ожидающие дочерние задачи не завершатся. Затем приостановить их тоже.
4. Проверить процессы и состояния задач, а не только отсутствие heartbeat.
   Не освобождать слот очереди принудительно, пока исполнитель может работать.
5. Остановить доступ приложения на запись на время резервного копирования и
   установки. Сделать полную резервную копию БД, включая `public` и
   `select_market`, сохранить media и проверить возможность восстановления.

В данном compose backend монтируется с хоста (`services/backend:/app`): копирование
кода в рабочую папку сразу делает его видимым старым процессам. Поэтому подготовить
релиз отдельно и заменять файлы только после остановки обслуживающих процессов.
Полный откат БД восстановит состояние на момент копии: записи, сделанные позднее,
потребуют отдельного сохранения. До окончания приёмки доступ на запись ограничен.

## 4. Установить и проверить миграции

Команды ниже — для существующего compose в корне платформы. PostgreSQL и остальные
зависимости должны работать. Фактические имена сервисов/путь сверить с сервером.

```sh
docker compose stop django frontend
# Здесь установить согласованный комплект и сохранить серверный .env.
docker compose build django frontend
docker compose run --rm --no-deps django python manage.py check
docker compose run --rm --no-deps django python manage.py showmigrations organizations datasets select_market
docker compose run --rm --no-deps django python manage.py migrate --plan
```

Сначала прочитать план. Обычный `migrate` включает ВСЕ ожидающие миграции, в том
числе СПС и других приложений; не продолжать при несогласованных изменениях.
Не использовать `--fake` для обхода ошибок. После проверки плана:

```sh
docker compose run --rm --no-deps django python manage.py migrate
docker compose run --rm --no-deps django python manage.py migrate --check
docker compose up -d --no-deps django frontend
docker compose exec django python manage.py check_select_market_iprice
docker compose logs --tail=100 django frontend
```

`check_select_market_iprice` не запускает загрузки. Он не гарантирует наличие
закупочных цен для каждой пары «код + регион»: покрытие проверить пробным расчётом.
Отсутствие сайта/классификации допускается, отсутствие расчётных входов — ошибка строки.

Если сервис запускается вне Docker, те же `python manage.py ...` выполняются
в серверном окружении с установленными зависимостями. Docker сам по себе не
меняет смысл миграций; важны версия кода, настройки и выбранная БД.

## 5. Согласованно включить общую очередь

- Пока исполнители не обновлены, сохранить `PARSER_SHARED_QUEUE_ENABLED=0`,
  новые запуски остаются запрещены. Селект Маркет при этом парсеры не запустит.
- После остановки всех старых процессов установить `PARSER_SHARED_QUEUE_ENABLED=1`
  во всех окружениях backend/команд, которые запускают парсеры. Пересоздать
  соответствующие контейнеры и перезапустить внешние исполнители, если обновлены.
  Простого `docker compose restart` недостаточно для чтения изменённого `.env`.
- Возобновить обработчик ТАРА и проверить два последовательных запуска:
  первый занимает слот, второй ожидает, после завершения первого второй стартует.
  Ожидание удалённой ТАРА не должно освобождать слот.
- Проверить `SELECT_MARKET_IPRICE_YML_URL`: если переменная отсутствует/пуста,
  применяется XML Селект Маркета. Старое переопределение на сайт Ай-Пласта удалить.
  Адрес Ай-Пласта при этом не меняется.

Выключение флага очереди во время работы задач не является безопасным откатом:
старый режим Ай-Пласта обходит очередь. Сначала завершить/подтвердить остановку задач.

## 6. Приёмка перед открытием доступа

- Ай-Пласт: открыть существующую версию, сравнить производство, транспорт,
  шесть типов цен и Excel с контрольной выгрузкой до обновления; выполнить
  отдельный пробный расчёт без изменения ранее утверждённой версии.
- Селект Маркет: загрузить полный датированный прайс и закупочную стоимость/
  параметры за нужный месяц; проверить текстовые коды и группы 1–4.
- Проверить аналог/эксклюзив, товар без сайта, без классификации, два региона,
  доставку включённую/выключенную и отсутствующую закупочную цену.
- Проверить индивидуальную и массовую правку только доставки; целые цены без/с
  НДС; маржу после округления всех оптовых уровней; совпадение таблицы с Excel.
- Согласовать цену, изменить параметры: старое согласование сохраняет суммы,
  версия требует повторного согласования. Повторное согласование даёт новую ревизию.
- Проверить зрителя/редактора, две организации в разных вкладках, отсутствие
  смешения данных, сохранение прав Ай-Пласта и работу обновлений интерфейса.
- Старые версии автоматически не пересчитываются. Новые правила проверять на
  новой версии. Автоматической отправки цен в 1С нет.

После успешной приёмки открыть доступ и возобновить расписания. Наблюдать первый
полный цикл парсеров и расчёта: ошибки, зависшие слоты, длительность и нагрузку БД.

## 7. Если перенос не прошёл

Не запускать новую работу и не повторять миграции вслепую. Сохранить сообщения
ошибок и фактический `showmigrations`. Восстановить согласованную пару старого кода
и резервной БД по отрепетированному на стенде плану. Откат только кода после
удаления полей 0009–0012 несовместим с прежними моделями.
Обратимые миграции предусмотрены, но их фактический план зависит от других
приложений; не выполнять универсальную команду отката на рабочей БД.

Для прерванной задачи сначала диагностика без изменения состояния:

```sh
docker compose exec django python manage.py recover_select_market_calculation --snapshot-id ID
docker compose exec django python manage.py recover_parser_queue --help
```

Операции восстановления со снятием блокировок выполняются только после проверки
завершения исполнителя и с фиксацией оператора/причины. После отката возобновлять
расписания только когда весь комплект исполнителей соответствует восстановленной версии.
