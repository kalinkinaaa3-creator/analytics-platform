# iPrice Селект Маркета: состояние внедрения

Актуальный порядок переноса и результаты проверки совместимости с Ай-Пластом:
[IPRICE_ROLLOUT.md](IPRICE_ROLLOUT.md). Перенос на рабочий сервер ещё не выполнялся.

> В работе изменение бизнес-контракта по фактическому прайсу Селект Маркета.
> Прежний перечень ниже относится к реализации до этого изменения и не означает
> готовность нового сценария к переносу. Уже изменены загрузка прайса (дата в форме,
> четыре группы справа налево, четыре цены с НДС, исходные суммы и целые цены без
> НДС), модель источника и шаблон. Миграция 0006 добавляет поля без удаления истории.
> Источник сайта по умолчанию заменён на XML Селект Маркета.
>
> Полный прайс, региональная закупочная стоимость, опциональная доставка,
> индивидуальные/массовые правки и целые итоговые цены без/с НДС подключены.
> Устаревшие модели и поля исключены из активных моделей; миграции 0009–0012
> сохраняют их значения в архиве. До переноса требуется прогон миграций на
> PostgreSQL, проверка конкурентных операций и приёмка на реальных источниках.
> Без классификации товар не исключается: предупреждение, без автоматических
> аналогов, расчёт от закупочной стоимости при наличии необходимых параметров.
> Фильтры должны включать оба независимых набора: группы 1С 1–4 из прайса и
> поля классификации, как в iPrice Ай-Пласта. Совместный отбор с поиском,
> взаимозависимые варианты, отдельный отбор без классификации и пустых уровней
> групп; та же область отбора используется при массовом редактировании.
> До завершения этих изменений не переносить этот промежуточный этап на рабочий сервер.

Продолжение: `iprice_catalog.build_products` подключён для Селект Маркета и
формирует товары версии по полному прайсу, не исключая неклассифицированные коды
и товары без сайта. Их ключ сайта пустой, предупреждения сохраняются в версии.
Группы 1–4 сохраняются в снимке. Фильтры групп и классификации подключены к таблице
React и API строк; варианты взаимозависимы и учитывают поиск. Новый региональный
расчёт подключён: товары без сайта получают строки по регионам прайса, отсутствие
закупочной цены отмечается ошибкой строки. Массовые изменения используют тот же
набор групп и классификаций. Анализ рынка поддерживает те же фильтры и выбор
группировки: четыре уровня групп 1С или классификация iPrice. Сравнение двух
версий также поддерживает фильтры. Для существующих строк используются данные
выбранной версии, для удалённых региональных строк — данные старой версии.
Взаимозависимые варианты включают удалённые товары и регионы; старая группа
сохранившейся строки не предлагается, если в новой версии эта группа изменилась.

Региональная экономика подготовлена отдельно в `iprice_regional_calculation.py`:
закупочная цена плюс введённая логистика только при включённом переключателе,
четыре типа цен без/с НДС с математическим округлением. `build_regions` проверен
на товарах без сайта, двух регионах с разной доставкой и отсутствии закупочных
цен. Он подключён к основному построителю и пересчёту после ручных/массовых правок.
Утверждение проверяет четыре типа цен. Excel и карточка React показывают четыре
цены без/с НДС; завод и дистрибьюторские цены из этих экранов/выгрузки убраны.
История ручных цен сохраняется на прежних ID строк; смена аналогов требует
повторного подтверждения. При редактировании используются сохранённые входные
значения версии, а не позднее перезагруженный прайс или закупочная цена.

Загрузки `product_cost` и `calculation_config` уже направлены в новую таблицу
`IPriceRegionalInput` (миграция 0008): месяц + текстовый код + регион. Стоимости
полностью заменяются только за месяц файла; предыдущие месяцы и настройки
доставки сохраняются. Параметры обновляют только указанные пары. Шаблоны API и
описания React обновлены. Старые таблицы заменены архивом миграциями 0009–0012,
описанными ниже; новый расчёт их не использует.

Последняя проверка этого промежуточного этапа: 174 теста, из них 169 прошли,
5 пропущены до PostgreSQL; ESLint и production-сборка прошли. Рабочая БД не изменялась.

Excel: `test_iprice_excel_roundtrip.py` скачивает через API все пять шаблонов,
заполняет их, загружает обратно и проверяет БД; отдельно выполняет расчёт и
проверяет итоговый Excel через API выгрузки. Проверены текстовые коды, группы,
НДС, даты Excel/ISO, доставка, классификация и префиксы, отказ от пустых файлов,
формул и недопустимой точности без частичной перезаписи. Это программная проверка
XLSX через openpyxl, а не ручной прогон в настольном Microsoft Excel.
Шаблоны имеют пояснения в комментариях заголовков, текстовые форматы идентификаторов,
форматы дат и закреплённую строку заголовков. Второй лист и примерные строки
не добавляются: загрузчики принимают один лист с фактическими данными.
Итоговая выгрузка расчёта — отчёт, а не файл для повторной загрузки вместо шаблона.

После аудита 15.10.2026 исправлены отдельное изменение доставки через API,
заполнение сводных цен после первоначального расчёта и подписи предупреждений React.
Изменение параметров снимает актуальность прежнего ручного согласования,
сохраняя его суммы, автора, дату и ревизию. Строка получает предупреждение о
повторном согласовании; до него утверждение всей версии запрещено. Новое ручное
согласование создаёт следующую ревизию, а не переписывает предыдущую.
При расчёте минимальная маржа проверяется для целых цен каждого уровня:
при необходимости РРЦ повышается до значения, обеспечивающего минимум после
округления скидок. Ручная цена и утверждение версии также проверяют этот минимум.
Регрессионные проверки покрывают сохранность истории, повторные изменения до
согласования, откат отклонённой ручной цены и первоначальную сводную цену.
Браузерный сценарий на подменённых API дополнительно проверяет тексты предупреждений.
Ранее сохранённые версии автоматически не переписываются: для применения нового
расчёта нужно создать новую версию. Миграций для этих исправлений не требуется.
Проверены сравнение с изменившейся классификацией, удалённый регион товара,
удалённый товар, пустые группы и отсутствие классификации. API вариантов фильтров
проверен вместе с API сравнения; браузерный сценарий выбирает группу при сравнении.
Добавлен PostgreSQL-тест полного перехода 0008 → 0012 → 0008 → 0012:
архив, две маршрутные строки, ID и суммы утверждений, активная версия,
исходные цены и восстановление последовательности ID. Локально он не выполнен.
Реальный Excel повторно проверен без загрузки в БД: 555 строк, 555 текстовых
кодов, регион Москва, корневая группа «Торговый ассортимент», все четыре цены

После очистки валидации загрузок и добавления теста диагностики отдельно прошли
33 теста источников и операций. Браузерная проверка включает смену группировки 1С/iPrice.
Браузерный сценарий прошёл, включая передачу переключателя доставки и суммы
12,34 руб. при предварительном просмотре и применении массовой правки.
Устаревшие загрузки отдельной номенклатуры и маршрутов отключены в API и React;
их старые тесты заменены проверкой отказа и проверками нового регионального источника.
Диагностика готовности больше не требует этих таблиц, сайта или классификации:
последние два источника дают предупреждение. Проверяется наличие полного прайса,
наличие закупочных цен за его месяц выводится отдельно (это не проверка покрытия всех пар).

Миграция 0011 архивирует и удаляет восемь дистрибьюторских полей региональных

Общие функции утверждения/выгрузки работают с четырьмя типами цен для Селект
Маркета, прежний контракт Ай-Пласта сохранён. Сводка оптовых цен округляет цены
каждой строки до целого перед вычислением медианы.
Миграция 0012 архивирует и удаляет departure, маршрутную стоимость и ID старых
источников маршрута. Для сохранения разных исторических строк используется
неизменяемый `historical_variant` (хеш старого маршрута); для новых строк он пустой.
Уникальность новых строк: товар + регион. Старые строки не объединяются, их ID
и ручные утверждения сохраняются. Исторические версии с маршрутами доступны для
просмотра/экспорта; изменения и повторное утверждение требуют нового расчёта.
React скрывает соответствующие действия, backend проверяет ограничение отдельно.
Сравнение Селект Маркета использует код 1С вместо ключа сайта, чтобы товары без
карточки сайта не объединялись по пустому ключу.
Проверены архивирование/восстановление двух маршрутов, независимость их строк,
запрет изменения и утверждения, выгрузка истории, сравнение разных кодов без сайта.
ESLint, сборка и браузерный сценарий (включая исторический режим) прошли.
Также остаётся применение миграций на отдельном PostgreSQL-стенде.

## Подключено

| Область | Реализация |
| --- | --- |
| Хранение | Собственные таблицы `select_market`, общий расчётный код и авторизация платформы |
| Коды | Текстовые коды 1С, включая ведущие нули и буквы; точная фильтрация не преобразует их в число |
| Источники | XLSX: полный прайс с группами за дату по всем регионам, закупочные цены, региональные параметры доставки/расчёта, префиксы, классификация/аналоги |
| Парсеры | YML, PS, ТопТара, ТАРА; общий слот двух организаций, сохранение слота при ожидании Windows-исполнителя |
| Расчёт | Фоновый запуск, REPEATABLE READ на PostgreSQL, одна незавершённая версия, сохранение предыдущего успешного расчёта при ошибке |
| Ручная цена | РРЦ с обязательной причиной, производные оптовые цены по скидкам строки, история и проверка конкурирующей правки |
| Параметры | Предварительный просмотр области по точным фильтрам, применение коэффициентов/скидок, общий пересчёт, сохранение ручных цен и истории |
| Утверждение | Права редактора, проверка ошибок и положительных итоговых цен, единственная активная версия, история утверждения и снятия |
| Защита утверждённых цен | Активную и ранее утверждённую версию нельзя редактировать; требуется новый расчёт |
| Выгрузка | Excel выбранной успешной версии, итоговые ручные цены, лист ошибок, сохранение текстовых кодов и защита строк от Excel-формул |
| Анализ | Сравнение версий, иерархия групп до товаров, текущая цена и итоговая РРЦ относительно рынка, настраиваемые пороги зон |
| Аналоги | Выбор активных конкурентов той же классификации, режимы авто/включить/исключить, история, пересчёт и повторное подтверждение ручных цен |
| React | Разделы «Главная», «Цены», «Рынок и изменения», «Расчёты и история», «Исходные данные»; права просмотра/редактирования |
| Восстановление | Административная команда использует тот же advisory lock, что и worker; живой расчёт не прерывается |

Отправки цен в 1С нет. SPS SKU и код 1С совместимы как строки, но этот этап
не создаёт и не обновляет товары СПС автоматически.

## Архив руководителя

Из `iprice-frontend.zip` переиспользованы компонент ценового коридора и форматирование.
Организация разделов и сценарии ручной цены, изменений, рынка и утверждения
адаптированы к существующей странице платформы. Демо-данные, второй вход,
переключатель организаций и отдельный Docker не переносились.

Основные сценарии подключены к реальным API: переходы по группам, редактор аналогов,
пороги зон, карточка расчёта и оптовых цен, справка, ручная цена, параметры, история,
сравнение и утверждение. Справка описывает фактический процесс платформы. Самостоятельная
шапка, авторизация и обещание отправки в 1С из демонстрации заменены существующими
механизмами платформы. Внешний вид не является точной копией демо: таблицы и формы
остаются в стилях Селект Маркета, ценовой коридор переиспользован из архива.

## Границы проверенного

Исторический прогон до смены бизнес-контракта: **132 теста прошли, 4 пропущены до PostgreSQL**
(136 всего). Актуальные результаты указаны в начале документа. ESLint компонентов,
production-сборка и браузерный сценарий прошли.
Сборка сохраняет предупреждение Vite о размере общего bundle платформы.

Дополнительная итоговая проверка: 13 тестов операций прошли, включая новый тест
на 1 000 региональных строк: страница содержит 50 строк, число SQL-запросов не
превышает пяти. Это проверка пагинации и отсутствия запросов на каждую строку,
а не замер производительности PostgreSQL под параллельной нагрузкой.
Браузерный сценарий также проверяет изменение версии другим пользователем:
утверждение блокируется до явного обновления данных. Сервер повторно проверяет
ожидаемую редакцию при утверждении.

- SQLite: тесты импортов, изоляции моделей, общей очереди, алгоритмов, ручных правок,
  истории, восстановления и API. Внешние источники заменены заглушками.
- React: ESLint, production-сборка и браузерный сценарий с ответами-заглушками:
  выбор аналога → ручная цена → предварительный просмотр параметров → применение → рынок и группы →
  утверждение → проверка прав зрителя.
- `makemigrations select_market datasets --check --dry-run` не нашёл расхождений
  моделей и миграций. Это не проверка применения миграций.
- На этой машине нет работающего PostgreSQL/Docker. Конкурентные транзакции,
  реальные схемы и применение миграций здесь не подтверждены. Подготовлены
  `iprice_postgres_settings.py` и `test_iprice_postgres.py` для отдельной тестовой БД.
- Текущий Excel экспортирует расчёт с диагностикой; это не контракт файла импорта
  в 1С. PDF в данный контур не добавлен.
- История утверждений хранится в JSON версии. Она защищена прикладными операциями,
  но не отдельным неизменяемым журналом PostgreSQL.
- Согласованное чтение БД не является полным архивом входных данных для повторного
  расчёта. Успешный расчёт следует запускать после завершения обновления источников.

## Подготовка переноса

1. Сделать резервную копию БД и сохранить текущую сборку приложения.
2. Проверить миграции и сценарии на отдельном PostgreSQL-стенде, не на рабочей БД.
   Настройки `select_market.iprice_postgres_settings` используют только переменные
   `IPRICE_TEST_HOST`, `IPRICE_TEST_PORT`, `IPRICE_TEST_USER`, `IPRICE_TEST_PASSWORD`.
   Django создаёт отдельную БД `test_iprice_acceptance`; пользователь тестов должен
   иметь право её создать. Не использовать это имя для рабочих данных.

   ```sh
   python manage.py test select_market.test_iprice_postgres --settings=select_market.iprice_postgres_settings
   ```

3. Остановить новые запуски старых парсеров/Airflow и дождаться завершения уже
   работающих процессов обеих организаций, включая Windows-исполнителя ТАРА.
   Старый процесс не знает новой очереди: одного переключения флага недостаточно.
4. Перенести согласованный комплект backend/frontend. Проверить план миграций:

   ```sh
   docker compose run --rm --no-deps django python manage.py migrate --plan
   docker compose run --rm --no-deps django python manage.py migrate
   ```

   План включает все ожидающие миграции репозитория, в том числе других приложений:
   состав релиза нужно сверить до выполнения команды.
5. Оставить `PARSER_SHARED_QUEUE_ENABLED=0` до согласованного обновления всех
   исполнителей и проверки. Затем установить `PARSER_SHARED_QUEUE_ENABLED=1`
   в окружении всех процессов, запускающих парсеры, и перезапустить их.
   Сохранить работу периодического `process_tara_jobs`.
6. `SELECT_MARKET_IPRICE_YML_URL` и `IPLAST_IPRICE_YML_URL` задают источники сайтов
   соответствующих организаций. Обе переменные обязательны для их загрузчиков;
   встроенных адресов и подстановки другого источника нет. Реальные URL хранить только в окружении.
   Проверить наличие СУЦ (`component=suc`) у
   Селект Маркета и назначение прав пользователям.
7. Выполнить диагностику без запуска загрузок:

   ```sh
   docker compose exec django python manage.py check_select_market_iprice
   ```

8. Загрузить реальные XLSX, проверить текстовые коды, принадлежность регионов и
   полноту классификации. Обновить источники, дождаться завершения, рассчитать
   пробную версию. Сверить вручную минимум: эксклюзив, аналог, несколько регионов,
   отсутствующая себестоимость, ручная цена, оптовые скидки, сравнение и Excel.
9. Проверить одновременно две организации: данные и версии не смешиваются,
   второй парсер ожидает общий слот, зритель не изменяет цены, повторное утверждение
   не меняет историю. Затем разрешить регулярные запуски.

## Восстановление прерванного расчёта

Сначала посмотреть состояние:

```sh
python manage.py recover_select_market_calculation --snapshot-id ID
```

После выяснения причины пометить незавершённый расчёт ошибочным:

```sh
python manage.py recover_select_market_calculation --snapshot-id ID --fail --operator "Имя администратора" --reason "Причина восстановления"
```

Команда откажет, если worker удерживает lock. После восстановления новый расчёт
запускается обычной кнопкой. Запоздавший worker увидит `failed` и не пересчитает
восстановленную версию. Для зависшего парсера используется отдельный протокол
`recover_parser_queue`; снятие его блокировки требует проверки остановки процесса.
