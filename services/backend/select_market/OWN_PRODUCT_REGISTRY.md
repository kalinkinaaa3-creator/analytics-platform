# Постоянные ключи собственных товаров Селект Маркета

Миграция 0014 расширяет `parser_product_url`: текстовый `own_code`, признаки
`in_price` и `on_website`; URL допускает NULL. Уникальность кода обеспечена
частичным ограничением БД только для `source=base`. Конкуренты и Ай-Пласт
продолжают использовать прежний механизм идентификации.

## Перенос

Сначала остановить новые загрузки прайса и запуски парсеров Селект Маркета,
дождаться завершения уже запущенных. Использовать резервную копию БД и новую
сборку кода для всех процессов Django/обработчиков. Команды из каталога проекта:

```sh
docker compose run --rm --no-deps django python manage.py migrate --plan
docker compose run --rm --no-deps django python manage.py migrate
docker compose run --rm --no-deps django python manage.py reconcile_iprice_products
docker compose run --rm --no-deps django python manage.py reconcile_iprice_products --apply
docker compose run --rm --no-deps django python manage.py reconcile_iprice_products
```

`migrate` применяет все ожидающие миграции проекта: проверить план, особенно
если на сервер переносится также другой незавершённый функционал. Команда
реестра затрагивает только Селект Маркет. При запуске без Docker префикс —
`python manage.py`, из окружения бэкенда с теми же настройками и БД.

Запуск без `--apply` проверяет заполнение в транзакции и откатывает изменения.
В PostgreSQL такой запуск может расходовать номера sequence новых записей:
пропуски номеров нормальны, существующие ID не меняются, sequence сбрасывать нельзя.
`bound` — число заполненных старых ключей, `created` — новые товары из прайсов,
`price_only` — текущие товары без сайта, `inactive` — отсутствующие в обоих источниках.
Повторный запуск после применения должен показать `bound=0`, `created=0`.

Код старой записи определяется по истории `base_product_price` и сверяется с
уже заполненным `own_code`. Нулевое число кодов, несколько кодов на ID или
один код на разные ID останавливают операцию целиком. Автоматического слияния нет.
Исходное наличие сайта берётся из старых признаков `status=active` и `is_loaded`;
после переноса рекомендуется успешная полная загрузка XML для актуализации.
До её завершения не запускать новый расчёт. После проверки возобновить загрузки.

## Поведение

- Последний полный прайс по дате задаёт `in_price`. Историческая загрузка
  может зарегистрировать ранее неизвестный ключ, но не заменяет актуальный состав.
- Полный успешный XML задаёт `on_website`. Частичная загрузка не снимает наличие
  с пропущенных позиций; неудачная загрузка откатывается.
- Ключ не зависит от региона и URL. Несколько строк XML с одним кодом или
  попытка передать URL другому коду отклоняются.
- Запись активна, пока присутствует хотя бы в одном источнике. Классификация
  и связи сохраняются при исчезновении; ручное отключение классификации не отменяется.
- Наличие в новом расчёте определяет прайс на дату расчёта. Классификация и
  аналоги берутся через постоянный ключ без обязательной записи цены сайта.
- Цены и свойства `base` создаются только из настоящего XML. Неизвестные
  характеристики не заменяются нулями. Сохранённые расчёты не переписываются.

Шаблон «Классификация и аналоги» содержит активные собственные товары и уже
классифицированных активных конкурентов. `code_1c`, `name`, `on_website` —
справочные столбцы, привязка выполняется по `product_key`. Новые строки требуют
заполнения классификации и группы аналогов; файл по-прежнему полный.
Старый формат без трёх справочных столбцов поддерживается.

Проверить на PostgreSQL-стенде: миграцию и ограничения URL/кода, параллельные
загрузки (RegistryConcurrencyTests), а также цикл прайс → сайт → исчезновение
→ возвращение с неизменным ID. Локальный SQLite не подтверждает блокировки PostgreSQL.
